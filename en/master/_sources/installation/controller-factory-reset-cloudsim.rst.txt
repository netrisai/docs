Controller Factory Reset (CloudSim Only)
==========================================

.. contents:: Table of Contents
   :local:
   :depth: 3

What "factory default" means here
-----------------------------------

Factory default = the controller database in the same state it's in immediately after a fresh install, before any Terraform/manual configuration is applied. In practice this is achieved by restoring a MariaDB snapshot taken right after a fresh install, rather than by reinstalling the controller. Reinstalling from scratch works too, but it's much slower and should only be needed to recover from a corrupted snapshot — restoring a known-good snapshot is the normal path.

There are two separate things to reset, managed by two different tools:

1. **The controller's database** — sites, IPAM, switches, users, etc. Reset by dropping and restoring MariaDB.
2. **The CloudSim switch/SoftGate/server VMs** (``netris-cloudsim/``) — managed by **Pulumi** (``pulumi up`` / ``pulumi destroy``). If they're left running against an old database, their IDs/state won't match after the DB is restored, so they need to be torn down and rebuilt.

.. tip::

  Don't confuse Pulumi with OpenTofu/Terraform (``tofu``).

  A separate project, ``netris-init/netris-spectrum-x-init/,`` uses OpenTofu to declare objects — switches, links, BGP sessions, etc. — inside the controller's database via the Netris API/Terraform provider. ``tofu apply`` / ``tofu destroy`` only ever create or remove rows in the controller's database; they never touch VMs.

  ``pulumi up`` / ``pulumi destroy`` brings up and tears down the VMs, but never touches the controller's database. Destroying or recreating one does nothing to the other.

.. warning::

  **Neither Pulumi nor Tofu gets you to factory default on its own — only a DB restore does.** ``pulumi destroy`` + ``tofu destroy`` makes the controller look empty, but the database underneath is not factory default: for example, VPC/Site/switch IDs that were used and then deleted stay reserved and can't be reused. If you need a genuinely clean controller — matching IDs, matching migration state, etc. — restore the database using the procedure below.

Part 1 — One-time setup: create the "golden" snapshot
--------------------------------------------------------

This only needs to be done once per controller version. The resulting ``.sql`` file is what you restore each time you need the environment back to a clean starting point.

Before taking the snapshot, make three changes so they're baked into every restore:

1. **Apply the license key** — Settings → General → Netris Auth Token.
2. **Set a real admin password** — replace the default with a random one.
3. **Set the Controller Management Address** — Settings → General → "Controller Management Address" (e.g. ``10.8.0.2``, the controller's IP as seen by switches/SoftGates). If left blank, the switch/SoftGate one-liner ("Install Agent" from Network → Inventory) fills the controller address in from whatever URL is in the browser bar — fine for real deployments, wrong for CloudSim, where the actual internal IP needs to be baked in so agents installed by hand still register correctly.

Then, SSH to the controller host and take the dump:

.. code-block:: shell

  kubectl -n netris-controller exec -it netris-controller-mariadb-0 -- \
    bash -c 'mysqldump -u $MARIADB_USER -p${MARIADB_PASSWORD} $MARIADB_DATABASE' \
    > db-snapshot-<version>.sql

``<version>`` is just a naming convention (e.g. ``db-snapshot-4.13.0.sql``) so snapshots can be told apart across controller versions.

Part 2 — The reset (do this every time)
------------------------------------------

Step 0 — if CloudSim VMs already exist, tear them down first
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

If CloudSim VMs are already running against the current (dirty) database, destroy them **before** touching the database — otherwise the switch agents keep trying to reconnect with IDs that no longer match after the restore.

.. code-block:: shell

  cd netris-cloudsim/
  pulumi destroy

.. warning::

  Do not run ``pulumi stack rm main`` after ``pulumi destroy`` unless instructed by Netris support — that can break the simulation environment. ``pulumi destroy`` alone is the safe way to stop a simulation.

Step 1 — drop and restore the database
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

SSH to the controller host, then:

.. code-block:: shell

  # Drop the current DB and create an empty one
  kubectl -n netris-controller exec -it netris-controller-mariadb-0 -- \
    bash -c 'mysql -u root -p${MARIADB_ROOT_PASSWORD} -e "DROP DATABASE $MARIADB_DATABASE"'
  kubectl -n netris-controller exec -it netris-controller-mariadb-0 -- \
    bash -c 'mysql -u root -p${MARIADB_ROOT_PASSWORD} -e "CREATE DATABASE $MARIADB_DATABASE"'

  # Copy the golden snapshot into the MariaDB pod and restore it
  kubectl -n netris-controller cp db-snapshot-<version>.sql netris-controller-mariadb-0:/opt/db-snapshot.sql
  kubectl -n netris-controller exec -it netris-controller-mariadb-0 -- \
    bash -c 'mysql -u root -p${MARIADB_ROOT_PASSWORD} $MARIADB_DATABASE < /opt/db-snapshot.sql'

.. tip::

  You can turn the above into a script. Here is an example, ``restore-db.sh``:

  .. code-block:: shell

    #!/usr/bin/env bash
    set -euo pipefail

    if [[ $# -ne 1 ]]; then
      echo "Usage: $0 /path/to/db-snapshot-<version>.sql" >&2
      exit 1
    fi

    SNAPSHOT="$1"

    if [[ ! -f "$SNAPSHOT" ]]; then
      echo "Error: snapshot file not found: $SNAPSHOT" >&2
      exit 1
    fi

    NAMESPACE="netris-controller"
    POD="netris-controller-mariadb-0"

    echo ">> Dropping and recreating \$MARIADB_DATABASE on $POD"
    kubectl -n "$NAMESPACE" exec -i "$POD" -- \
      bash -c 'mysql -u root -p${MARIADB_ROOT_PASSWORD} -e "DROP DATABASE $MARIADB_DATABASE"'
    kubectl -n "$NAMESPACE" exec -i "$POD" -- \
      bash -c 'mysql -u root -p${MARIADB_ROOT_PASSWORD} -e "CREATE DATABASE $MARIADB_DATABASE"'

    echo ">> Copying $SNAPSHOT into pod"
    kubectl -n "$NAMESPACE" cp "$SNAPSHOT" "$POD":/opt/db-snapshot.sql

    echo ">> Restoring snapshot"
    kubectl -n "$NAMESPACE" exec -i "$POD" -- \
      bash -c 'mysql -u root -p${MARIADB_ROOT_PASSWORD} $MARIADB_DATABASE < /opt/db-snapshot.sql'

    echo ">> Restore complete."

.. note::

  This matches the Rollback Procedure in :doc:`Standalone Controller Upgrade and Rollback (CloudSim Only) <standalone-controller-upgrade-rollback-cloudsim>`, with one difference: that page also has you stop the Netris agents on switches/SoftGates first (``sudo systemctl stop netris-sw`` / ``netris-sg``). Skip that for CloudSim — it's simpler to destroy and rebuild the VMs (Step 0 / Step 3) than to SSH into each one.

.. note::

  **Sanity check before relying on this snapshot:** confirm the controller version matches what you intended (Settings → General → Netris Version), then confirm the restored controller matches a known vanilla install and nothing more.

  A factory default database contains:

  - Two Tenants — **Admin** and **DevOps** — plus two users, **netris** and **system** (both Permit All / Edit All Tenants). No User Roles or Permission Groups.
  - One VPC — **VPC-1**, both System and Default, owned by the Admin tenant with Guest Tenants set to All.

  No other objects exists in a factory default database.

  If the restored controller has anything beyond this, the snapshot isn't clean — don't debug it, restore a different, previously-verified-clean snapshot instead.

Step 2 — clear any stale Terraform state for controller objects
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

If an OpenTofu/Terraform project was used to declare objects — switches, links, BGP, etc. — inside the controller, its state file is now stale: the DB restore just wiped out whatever it thought it had created. From that project's directory (either ``~/netris-init/netris-spectrum-x-init`` or ``~/netris-init/arista-veos-lab-init``:

.. code-block:: shell

  cd ~/netris-init/netris-spectrum-x-init
  rm *tfstate*

That removes both ``terraform.tfstate`` and ``terraform.tfstate.backup``, so the next ``tofu apply`` starts from zero instead of erroring out on drift.

Step 3 — rebuild the CloudSim VMs
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. code-block:: shell

  cd netris-cloudsim/
  pulumi up

The VMs come back up, install their agents, and phone home to the controller using the same unique per-node key baked into the snapshot — so they reconnect and register automatically.

``pulumi up`` also (re)installs a set of SSH aliases for the simulated nodes; run ``alias | grep ssh`` on the controller host to see them.

.. tip::

  If a node had been left running for a long time before being torn down, it can come back flapping (green/red/green) instead of settling — rebuild just that one node:

  .. code-block:: shell

    rebuild <node-name>

Step 4 — verify
^^^^^^^^^^^^^^^^

- Settings → General shows the expected version, and the license/password/management-address are the baked-in ones from Part 1.
- Network → Inventory, VPC, and Sites match the vanilla-controller checklist in Step 1 — nothing extra left over.
- OpenTofu, ``tofu plan``, should show it wants to create everything from scratch, not "no changes" or drift errors.

Notes and gotchas
-------------------

- **Don't reuse a snapshot without checking it first.** This procedure once hit a bug where a restored snapshot silently forced a migration version back to zero, which broke switch/link creation with an unhelpful ``"Unable to add hw"`` error. If that error shows up after a restore, don't debug it — restore a different, previously-verified-clean snapshot instead and re-derive a clean one for the current version: restore the last known-good snapshot, upgrade the controller to the target version (``curl -sfL https://get.netris.io | sh -``, run on the controller host), then take a fresh ``mysqldump`` of that upgraded, never-touched database as the new golden snapshot. That's cleaner than a snapshot taken after objects were built and deleted by hand, because object IDs (e.g. site IDs) are never reused.
- **OpenTofu apply normally runs with** ``-refresh=false`` **for speed** (``alias tofu-apply='time tofu apply -refresh=false -parallelism=10 -auto-approve'``). ``-refresh`` controls whether it re-checks each resource against the controller before planning: ``true`` queries current state and updates the state file first; ``false`` trusts the existing state file as-is. After a database reset, run it once with ``-refresh=true``, since the previous state file no longer matches reality.

.. warning::

  This procedure applies only to CloudSim (standalone) controllers. A real customer's production controller is virtually always HA, and there's no equivalent "wipe the DB and VMs" shortcut there. Don't treat this page as a production DR/rollback procedure; use the HA install guide's maintenance/upgrade sections for that.
